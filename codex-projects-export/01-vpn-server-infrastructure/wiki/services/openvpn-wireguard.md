# OpenVPN, WireGuard и AmneziaWG

`hometele` выполняет роль WireGuard hub `wg-home` для Keenetic/Home Assistant. Сеть `10.77.77.0/24` маршрутизируется через OpenVPN `tun79` к чешскому выходу `azazello`. PrivateKey и PresharedKey запрещено хранить в Git.

Ранее исправленная проблема Telegram в Home Assistant была связана с отсутствующим маршрутом `wg-home → tun79`; после исправления Telegram API доступен через чешский выход.

## Рабочий каскад AmneziaWG — 2026-07-18

Основной каскад Xray переведён на существующий сервер AmneziaWG на `azazello`:

- `azazello`: контейнер `amnezia-awg2`, UDP/39425, адрес сервера `10.8.1.0/24`;
- `hometele`: userspace-интерфейс `awg79`, адрес `10.8.1.2/32`, MTU `1280`;
- исходящий Xray outbound сохранил прежний tag `to-czech-openvpn`, но его `sendThrough` изменён на `10.8.1.2`;
- source-based routing ограничен точным правилом `from 10.8.1.2 lookup 180`; таблица 180 содержит `default dev awg79`;
- службы `awg-quick@awg79` и `awg79-policy-route` включены и активны;
- OpenVPN `tun79` не удалён, включён и активен как резервный канал.

Межсерверный peer зарегистрирован в постоянной конфигурации `awg0.conf`, таблице клиентов Amnezia и в работающем интерфейсе. На `azazello` установлен сторож максимального приоритета:

- `amnezia-hometele-peer-guard.service` запускается при старте сервера;
- `amnezia-hometele-peer-guard.timer` повторяет проверку каждые 30 секунд;
- служба сторожа имеет повышенный приоритет `Nice=-10` и `IOSchedulingPriority=0`;
- сторож восстанавливает только peer `hometele-cascade`, если панель или перегенерация удалит его из постоянной конфигурации, таблицы клиентов или live-интерфейса;
- при конфликте адреса `10.8.1.2/32` с другим публичным ключом сторож завершает работу с ошибкой и ничего не перезаписывает;
- защищённые ключевые данные хранятся только на сервере в `/etc/amnezia-hometele-peer/`, а резервные копии — в `/var/backups/amnezia-hometele-peer/`; секреты в WIKI не сохраняются.

Быстрое переключение на `hometele`:

```bash
sudo xray-egress-select status
sudo xray-egress-select openvpn  # немедленный возврат на tun79
sudo xray-egress-select awg      # возврат на AmneziaWG
```

Скрипт проверяет доступность выхода через выбранный source address, создаёт резервную копию конфигурации Xray, меняет только `sendThrough`, выполняет валидацию Xray и автоматически откатывает изменение при ошибке.

Контроль после переключения подтвердил:

- внешний адрес каскадного трафика — адрес `azazello`;
- YouTube `generate_204` через локальный SOCKS Xray возвращает HTTP 204;
- 20 МБ через прямой AmneziaWG передавались примерно со скоростью 67 Мбит/с, 10 МБ через Xray/SOCKS — примерно 32 Мбит/с;
- DF-пакет с полной длиной 1280 байт проходит без фрагментации;
- OpenVPN продолжает устанавливать отдельный рабочий выход через `azazello`.

Резервные копии перед внедрением:

- `hometele`: `/root/awg79-client-backup-20260718-085102` и `/root/awg79-cutover-20260718-085840`;
- `azazello`: `/root/amnezia-awg2-peer-hometele-20260718-085103`.

## Аудит `tun79` и параллельный WireGuard-тест — 2026-07-18

На момент этого аудита рабочий каскад `hometele → azazello` использовал OpenVPN UDP/21194:

- `hometele`: `tun79` = `10.79.0.2`, `azazello`: `tun79` = `10.79.0.1`;
- MTU интерфейса с обеих сторон равен `1500`, явные `tun-mtu` и `mssfix` в конфигурации отсутствуют;
- фактически OpenVPN уменьшает MSS исходящего TCP примерно до `1343`, поэтому явного black-hole MTU не обнаружено;
- контрольная скорость: напрямую с `hometele` около 164 Мбит/с, через `tun79` около 33 Мбит/с, напрямую с `azazello` около 347 Мбит/с;
- при передаче 50 МБ на `azazello` процесс OpenVPN занимал примерно 65–76% единственного vCPU, а `tun79 TX dropped` вырос на 3233 пакета.

Для изолированного сравнения поднимался `wg79test` без подключения к Xray:

- тестовая сеть `10.79.79.0/30`, MTU `1420`;
- ранний тест на UDP/443 временно работал; UFW разрешал порт только от публичного IP `hometele`;
- прямой UDP/51821 оказался нестабилен;
- RTT около 54 мс; в одновременной серии по 100 пакетов потери составили 1% для WireGuard и 2% для OpenVPN;
- в кратковременном успешном тесте скорость `azazello → hometele` достигала примерно 129 Мбит/с, `hometele → azazello` — примерно 88 Мбит/с;
- повторные чистые тесты на свободных UDP/46540 и UDP/21195 устанавливали handshake, пропускали только первые пакеты и затем теряли обмен; поведение соответствует фильтрации прямого WireGuard по сигнатуре;
- все созданные для теста правила UFW удалены, `wg-quick@wg79test`, `wg79test-egress` и `wg79test-policy-route` выключены и не включены в автозапуск;
- в рамках этого теста пользовательский трафик и Xray не переключались; позднее основной каскад был отдельно переведён на существующий AmneziaWG, а `tun79` сохранён резервом.

### Инцидент policy routing и восстановление

При подготовке source-based routing была ошибочно использована форма `ip rule add not fwmark ... from ...`. В `ip rule` оператор `not` инвертирует весь selector, а не только `fwmark`; правило с priority 10078 перехватило внешний ответный трафик `hometele` и временно сделало сервер недоступным по сети.

Доступ восстановлен через VNC удалением правила `sudo ip rule del priority 10078`. После восстановления служба `wg79test-policy-route` отключена, таблица 179 очищена, OpenVPN и Xray проверены. Не использовать сочетание `not fwmark` и `from` в одном правиле без отдельного live-теста с автоматическим откатом.

Резервные копии перед тестом остаются локально на серверах:

- `hometele`: `/root/wg79test-backup-20260718-002337`;
- `azazello`: `/root/wg79test-backup-20260718-002340`.

Дополнительные копии конфигурации перед финальным откатом:

- `hometele`: `/etc/wireguard/wg79test.conf.rollback-20260718-083734`;
- `azazello`: `/etc/wireguard/wg79test.conf.rollback-20260718-083735`.
